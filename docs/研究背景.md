# 港湾システム停止と手動運用を調べる背景

資料確認日：2026年11月17日。現行研究は、TOS停止時の手動FIFOと短い荷役優先を比べ、停止なしと復旧待ちを基準に置く構成。[研究設計](研究設計.md)に従って実装し、各10試行の[結果](実験結果と考察.md)を保存した。サイバー侵入や機器破壊の再現ではない。

## 1. 実事件で確認されたこと

国土交通省の[名古屋港事案の最終取りまとめ](https://www.mlit.go.jp/kowan/content/001719866.pdf)の第2節を確認した。2023年7月4日にNUTSの停止が確認され、6日にターミナルが順次再開した。搬出入は約3日停止した一方、紙の作業内容によって本船荷役を継続した。報告では37隻の荷役スケジュールに影響があり、最大約24時間の遅延が記載されている。これはバース待ち時間だけの実測値ではない。計画支援機能だけが停止したとも確認されていない。

紙で継続できた点は代替運用の根拠になるが、経験者への依存や、すべての作業を手動で行う準備の難しさも指摘されている。同報告はシステム障害時のBCPや、再開前の安全確認を求めている。今回の実験から37隻・24時間を再現したとは主張しない。

[Maerskの2017年第2四半期公式説明資料](https://investor.maersk.com/static-files/d737ac5a-eb8f-4e0b-aba7-0d4158226b29)の5ページでは、NotPetyaによりアプリケーションとデータが利用不能になり、予防的停止と手動の代替措置を取ったこと、船舶の制御は維持されたことが説明されている。停止する情報機能と、継続する物理業務を区別する参考とする。

[DP World豪州の2023年11月28日公式発表](https://www.dpworld.com/en/news/releases/australia/media-statement-update-on-cybersecurity-incident)では、10日の不正アクセス検知後、封じ込めのためインターネットから切断し陸側業務に影響が出た。13日の業務再開後、30,137個の滞留コンテナの解消は20日だった。ランサムウェアや暗号化は確認されていない。システム再開と滞留処理完了を分ける根拠であり、船舶の回復時間を直接与える資料ではない。

以上を合わせると、情報処理が使えない間に業務を見合わせる条件と、代替手順によって一部を継続する条件を比べる方向は説明できる。ただし、同じ事故で両方を比較した実験ではない。「復旧を待つ」は研究上の比較基準であり、一般的な現場対応と断定しない。

## 3. 資料からモデルへの簡略化

資料を踏まえた研究上の推論として、荷役に必要な情報確認・作業指示が制限される状態を、準備後に手動で同時運用できる船の上限で表す。その同じ能力で到着順と短い荷役優先を比較する。公的資料が具体的な同時対応数や準備時間を与えているわけではなく、準備2時間・同時上限2隻に固定した仮定として比較する。

同時運用上限は手動業務全体を集約した代理変数であり、確認件数や人員数を直接表さない。復旧後の記録処理も追加遅延として置かない。詳細な業務負担や実港の最適な切替時刻を測るモデルとは区別する。

港への入港、着岸、荷役開始、トラックの搬出入は区別する。これらを一つの「船が入れない」にまとめない。公的資料が手動作業をコンテナ単位で説明しているため、船ごとの確認時間へ集約する場合は、研究側の簡略化として記す。

現行コードは停止中の新規荷役開始を制限し、開始済みの荷役は継続する。到着・完了の即時観測と、到着済み船の正確な荷役見積りを仮定する。通常と復旧後は4バースのFIFOを使い、手動同時上限2隻・準備2時間の下で手動中の順序を変える。これはTOSのどの機能が何隻の運用に対応するかを実証した設定ではない。

## 4. 結果を使う判断と限界

想定利用者は、障害時の手順と人員を準備するターミナル運営者。限られた手動能力でどの船から開始するかを検討するため、平均待ちと長時間船の負担を比較する。現段階では、実際の切替時間、確認処理率、照合作業量の公開値は確認できていない。

通常の故障でも同じ機能制約なら同じ結果になる。攻撃者の利益・侵入確率・検知能力は研究対象外。攻撃固有の被害を証明する研究とは呼ばない。
