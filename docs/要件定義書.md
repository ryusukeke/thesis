## 1. この文書の位置づけ

現在の実装が「何を目的とし、どの条件で、何を行うシステムなのか」を要件として書き起こす。
実装を正解と決める文書ではなく、利用者が意図していた研究内容とのずれを確認するための現状整理である。
特に、元の計画にあった内容と、実装時に具体化した仮定を区別する。
仮定を正式な研究要件として採用するかは、個別に確認する。船ごとの係数の並べ替え方式は2026年10月7日にユーザーが採用した。その他の確認項目を一括して承認済みとは扱わない。

確認した資料は次のとおり。

- [simulation.py](../simulation.py)：データ生成、改ざん、割当、評価・集計。
- [run_experiment.py](../run_experiment.py)：実行条件、保存、画面表示。
- [test_simulation.py](../test_simulation.py)：自動テスト12件。
- [README](../README.md)、[実験設定](../results/config.json)、[予備比較レポート](予備比較レポート.md)。
- ユーザー提供の7月28日のゼミ報告PDF（`0728_2247040z_河田竜典.pdf`）。会話内で確認した8月前半〜9月後半の計画。
- 会話での方針：文系大学生が卒論で説明できる程度の実装とし、計算と出力を分離する。

以下では、要件の由来を4種類で示す。

| 区分 | 意味 |
| --- | --- |
| 計画・依頼 | 元の計画または会話の依頼に根拠がある |
| 既存実装の継承 | 今回の修正前から存在していた方式や指標を引き継いでいる |
| 実装具体化 | 計画の実現方法として、コードで具体的な方式や値を決めている |
| 追加支援 | 比較や説明をしやすくするために加えた機能 |

「実装具体化」は、研究上その選択が妥当だと確認済みという意味ではない。

## 2. システムの目的

船舶の申告到着時刻が改ざんされた場合に、バース割当と荷役の実行結果がどう変わるかを、正常時と比較できるようにする。
船の待ち時間・在港時間などの評価指標を複数回の試行で集計し、予備的な影響を確認する。

利用者は卒論研究を行う学生であり、自分のPCでPythonのコマンドを実行する。
研究者が実験条件を指定し、CSVやグラフを確認し、結果を卒論・ゼミ報告で説明する用途を想定する。

現在のシステムは、生成した船舶データに対するシミュレーションである。
実際の港への接続、実システムへの攻撃、実際の船舶運航の制御は対象に含めない。

## 3. 対象範囲

### 3.1 対象となる機能

1. 到着時刻と荷役時間を持つ船舶データの生成。
2. 正常時のバース割当と荷役時刻の計算。
3. 特定船1隻の申告時刻を早める・遅らせる改ざん。
4. 同じ船舶データを用いた正常時と攻撃時の比較。
5. 複数回の実験と、平均・ばらつき・正常時との差の集計。
6. 実験条件と結果の保存・表示。

### 3.2 現在の対象外

実データの取り込みと分布パラメータの推定、複数船の同時改ざん、実験途中の改ざん、改ざん検知、防御方式の比較、割当の全体最適化は実装していない。
船型・船長・水深・クレーン数・潮位・故障などの制約も扱わない。
画面操作用のGUI、ネットワークサービス、統計的な有意差検定は提供しない。

これらは現在の範囲の説明であり、今後も実装しないという決定ではない。

## 4. 用語と時間の定義

| 用語 | このシステムでの意味 |
| --- | --- |
| 船 | V1、V2、…で識別する仮想の船。試行ごとに到着時刻と荷役時間を生成する |
| バース | B1、B2、…で識別する荷役場所。同時に荷役できる船は1隻 |
| 実到着時刻 | 船が実際に到着する時刻。攻撃で変更しない |
| 申告到着時刻 | 割当計画が参照する到着情報。攻撃で変更する |
| 基準荷役時間 | 船ごとに生成し、各バースの荷役時間の計算で共有する基準値 |
| 荷役時間 | 指定バースでその船の荷役にかかる時間 |
| FCFS | 申告到着時刻が早い船から順に割当計画を作る規則 |
| 計画時刻 | 申告到着時刻を使って算出した開始・完了時刻 |
| 実行時刻 | 計画に実到着と直前の船の実完了を反映した開始・完了時刻 |
| 待ち時間 | 実到着から実荷役開始までの時間 |
| 在港時間 | 実到着から荷役完了までの時間。離岸・出港の時間は含めない |
| 試行 | 1組の船舶データについて、正常・早い申告・遅い申告を比較する単位 |

全時刻・時間の単位は時間とする。
最初の船の実到着時刻を0とし、実際の日付や時計の時刻は扱わない。
船番号は実在船のIDではなく、各試行の生成データ内の識別子である。

## 5. モデル上の前提

これらは実装に組み込まれている前提であり、研究上の採用確認が必要である。

| ID | 現在の前提 | 要件としての確認点 |
| --- | --- | --- |
| M-01 | 全船の申告時刻と全バースの荷役時間を持つ表から、割当計画を事前に作る | 船の到着に応じて順次判断する運用を研究したい場合は、別のモデルになる |
| M-02 | 計画は申告時刻だけで決め、実到着時刻は実行段階で使う | 改ざんの対象を「到着情報」としてよいか |
| M-03 | 計画後は各船のバースとバース内の順番を固定する | 未到着船を待つ間に別の船を入れる運用を許すか |
| M-04 | 実行時も計画開始より早く荷役しない | 遅く申告された船が既に到着していても、計画開始まで待つ想定でよいか |
| M-05 | 攻撃は計画作成前に対象船1隻の申告時刻を変更する | 運用途中の書換えや複数対象の攻撃は今回の研究範囲に含めないか |
| M-06 | 荷役時間は割当前に決まり、実行途中では変わらない | 荷役中の速度変動や故障などを含めない単純なモデルでよいか |
| M-07 | 全船がすべてのバースを利用できる | 船型などの利用制約を今回省略してよいか |

M-03とM-04は、攻撃の影響が生じる仕組みに直接関係する。
計画を作るだけでなく、この固定計画をどのように実行するかも研究モデルの一部となっている。

## 6. 機能要件

### FR-01：相関のある荷役時間と到着時刻を生成する

由来：計画・依頼と実装具体化。

指定した船数・バース数・seedから船舶データを生成する。
到着間隔は平均2.37時間の指数分布とし、累積した時刻を最初の船が0になるよう調整する。
船ごとの基準荷役時間は2-Erlang分布（shape=2、scale=2.4）から生成する。

```text
バース別荷役時間 = 船の基準時間 × バース係数 × (1 + 誤差)
```

複数バースの係数の組は0.9〜1.1の等間隔、1バースなら1.0とする。
船ごとに同じ係数の組をランダムに並べ替えて各バースへ配置し、船とバースの相性を表す。3バースなら0.9・1.0・1.1を1つずつ使う。配置はseedから再現可能とし、同じ試行の比較条件では変更しない。
配置した係数は元データの `berth_factor_B1` などに保存する。
誤差は各船・各バースで−0.05〜+0.05の一様乱数とする。
基準を共有するので、各バースの最終荷役時間は異なりつつ相関を持つ。

基準共有は元の計画にある方式だが、平均値・係数・誤差幅は現在の具体的な設定である。
目標とする相関係数は元の計画からは確定していない。

### FR-02：正常条件と2種類の攻撃条件を作る

由来：計画・依頼と実装具体化。

正常時は実到着時刻と申告時刻を同じにする。
攻撃時は、指定した対象船について実到着時刻を基準に申告時刻を早める、または遅らせる。
変更幅は両方向で同じ値とし、早めた申告時刻が0未満なら0に丸める。

元データ、実到着時刻、全バースの荷役時間、対象船以外の申告時刻は変更しない。
保存結果には元の実到着時刻、条件ごとの申告時刻、実際の変更幅を残す。

### FR-03：申告時刻順で割当計画を作る

由来：既存実装の継承と実装具体化。

申告時刻の早い船から割り当て、同時刻なら入力の行順を維持する。
生成データの入力行はV1、V2、…の順なので、生成データでは同時刻の船番号順に対応する。
バースは次の優先順位で選ぶ。

1. 計画開始時刻が最も早い。
2. 開始時刻が同じなら、計画完了時刻が最も早い。
3. 両方同じなら、バースの配列番号が小さい。

全船の総待ち時間や最終完了時刻を最小化する最適化問題は解かない。

### FR-04：到着とバース利用の制約を守って実行する

由来：実装具体化。

```text
計画開始 = max(申告到着時刻, バースの計画上の利用可能時刻)
実開始 = max(計画開始, 実到着時刻, バースの実際の利用可能時刻)
実完了 = 実開始 + 割当バースでの荷役時間
```

実到着前の荷役と、同じバースでの荷役の重複を認めない。
計画後のバースと順番は固定する。計画時刻と実行時刻を両方保存する。
未到着船を飛ばす再割当は行わない。

### FR-05：同じデータで複数回比較する

由来：計画・依頼と実装具体化。

指定試行回数だけ実験し、試行番号1では指定seed、以降は1ずつ増やしたseedを使う。
各試行の元データを1回生成し、正常・早い申告・遅い申告の3条件で共有する。
別の試行では新しい元データを生成する。

船別の正常時との差は船番号で、試行別の指標の差は試行番号で対応づける。
条件ごとの行番号で異なる船を比較しない。

### FR-06：実到着時刻を基準に評価指標を計算する

由来：既存実装の継承と追加支援。

待ち時間は `実開始 − 実到着`、在港時間は `実完了 − 実到着` とする。
申告時刻を評価の起点に使わない。
各試行・条件について次の8指標を計算する。

| 指標 | 意味 |
| --- | --- |
| 総待ち時間 | 全船の待ち時間の合計 |
| 平均待ち時間 | 全船の待ち時間の平均 |
| 最大待ち時間 | 全船の待ち時間の最大値 |
| 総在港時間 | 全船の在港時間の合計 |
| 平均在港時間 | 全船の在港時間の平均 |
| 全船の荷役完了時刻 | 各船の実完了時刻の最大値 |
| 対象船の待ち時間 | 指定した船1隻の待ち時間 |
| 対象船以外の平均待ち時間 | 対象船を除く船の平均待ち時間 |

### FR-07：平均、ばらつき、対応する試行の差を集計する

由来：計画・依頼と追加支援。

各条件・指標について、全試行の平均と標本標準偏差を計算する。
攻撃条件では、同じ試行の正常時の値を引いた差の平均・標本標準偏差・最小・最大を計算する。
指標が増加・減少・変化なしとなった試行回数も数える。

差の定義は `攻撃時 − 正常時` とする。
比較する8指標では、値が増えることを悪化として表示する。
±0.000000001時間以内の差は変化なしとする。
1試行だけの場合、標本標準偏差は未定義としてCSVを空欄にする。

### FR-08：実験条件を指定し、不正な設定を拒否する

由来：実装具体化と追加支援。

| コマンド引数 | 初期値 | 制約・意味 |
| --- | --- | --- |
| `--trials` | 100 | 整数、1以上 |
| `--ships` | 10 | 整数、2以上。他の船の平均を求めるため最低2隻 |
| `--berths` | 3 | 整数、1以上 |
| `--seed` | 42 | 整数、0以上 |
| `--attack-ship` | V5 | 生成される船番号V1〜Vnのいずれか |
| `--shift` | 4.0 | 0以上の有限値。内部で早い条件を負、遅い条件を正にする |
| `--output` | results | 保存先フォルダ |
| `--no-plot` | 指定なし | 指定時はグラフを作成しない |

到着間隔、荷役分布のパラメータ、係数範囲、誤差幅はコード内の定数とする。
コマンドからこれらを変更する機能は現在ない。
不正設定は実験開始前にエラーとして表示する。
上記の入力確認は、通常の実験入口 `run_experiment()` を利用する前提である。
個々の計算関数に任意の外部表を渡す場合の、全項目の検証は提供していない。

### FR-09：結果と条件を保存し、概要を表示する

由来：計画の比較を支える追加支援。

| 保存先内のファイル | 必須となる情報 |
| --- | --- |
| `ship_data.csv` | 各試行の元データ、実到着時刻、基準時間、船別・バース別の係数と荷役時間、試行番号、seed |
| `schedules.csv` | 条件ごとの申告時刻、割当順とバース、計画・実行時刻、待ち時間・在港時間、正常時との差、対象船フラグ、変更幅 |
| `run_metrics.csv` | 各試行・条件の8指標 |
| `summary.csv` | 各条件・指標の平均、標本標準偏差、試行回数 |
| `paired_comparison.csv` | 正常時との差の集計、増加・減少・変化なしの回数 |
| `config.json` | 入力条件、使用seedの範囲、分布条件、係数の組と配置方式、時間単位、実行方式、NumPy・Pandasのバージョン |

CSVはUTF-8 BOM付きとする。
正常時の元データと、攻撃時を含む各スケジュールを、試行番号・船番号で照合できるようにする。
保存先フォルダを作成し、同じ保存先では同名の結果ファイルを上書きする。
画面には実験条件、4指標の条件別平均、全船の平均待ち時間の差と変化の回数、保存先を表示する。

### FR-10：平均待ち時間をグラフで比較する

由来：追加支援。

全船と対象船以外の平均待ち時間について、3条件を比較する棒グラフをPNGで保存する。
棒は全試行の平均値とし、標準偏差や信頼区間の線は表示しない。
図中は英語表記とし、対象船・変更幅・試行回数をタイトルに含める。

`--no-plot` で無効化できる。
グラフを作成しない場合も過去の同名グラフを除去し、新しいCSVとの混在を避ける。
Matplotlib自体が未導入なら案内を表示し、CSV・JSONの保存を完了した状態で継続する。

## 7. 実装構成と品質に関する要件

### NFR-01：計算と出力を分離する

由来：会話での明示的な依頼。

`simulation.py` はデータ生成・改ざん・割当・評価・集計を行い、5つの表を返す。
ファイル保存、画面表示、コマンド引数、グラフ作成を担当しない。
`run_experiment.py` は計算を呼び出し、結果を表示・保存する。
計算ファイルを直接実行しても、実験や出力を始めない。

### NFR-02：卒論で説明できる構成にする

由来：会話での明示的な依頼。

計算処理を6関数、実行・出力処理を2関数に分け、関数と繰り返し処理を中心に構成する。
モデルの前提、計算式、各関数の役割、実験結果をMarkdown文書で説明する。
「説明できる程度」は利用者の理解に関わるため、コード量や関数数だけでは達成を判定しない。

### NFR-03：比較の再現性と物理的整合性を確認できる

同じ入力・seed・ライブラリ環境で計算を再現できることを確認する。
実到着前の荷役、負の待ち時間、同一バースでの荷役の重複を認めない。
改ざん幅0では正常時と各条件の結果が一致する。
元データ、設定、船別結果を保存し、集計だけでなく個別の変化も追跡できるようにする。

現状はNumPy・Pandasのバージョンを記録するが、Python・MatplotlibのバージョンやソースコードのコミットIDを結果JSONには記録しない。
環境全体を固定する仕組み、処理時間の保証、試行数の上限、出力の一括保存の保証は現在ない。
これらを追加必須の要件とするかは、今回の研究規模に応じて判断する。

## 9. ずれの確認で優先する項目

以下は不具合の断定ではなく、意図との一致を確認すべき論点である。
優先度は実験結果への影響の大きさから付けた。

| 優先度 | ID | 現実装 | 確認する内容 |
| --- | --- | --- | --- |
| 高 | C-01 | 割当順・バースを固定し、未到着船を待つ | 空きバースや空き時間を他の船で埋める再割当を省いてよいか |
| 高 | C-02 | 改ざんするのは申告時刻だけで、実到着は変えない | 研究したいのは情報改ざんか、実際の到着遅延・早着か |
| 高 | C-03 | 全船分の情報で事前計画し、計画開始を守る | 到着時点で判断する方式や、到着済み船を前倒しする運用を想定していないか |
| 中 | C-04 | 荷役時間の相関が強い | 基準共有は計画どおりだが、±5%の誤差で生じる相関の強さが意図に合うか |
| 中 | C-05 | 時間・係数は仮定した値 | 予備比較は仮定データでよいか、神戸港の個別船データによる推定まで必要か |
| 中 | C-06 | 早い申告の負時刻を0に丸める | 一部の試行で実変更幅が指定値より小さくなる条件で比較してよいか |
| 中 | C-07 | 対象V5、±4時間、10隻・3バース・100回が初期値 | この1条件が予備実験として十分か。条件を変えた追加比較が必要か |
| 低 | C-08 | 在港時間は荷役完了まで | 卒論で使う「在港時間」の定義がこの範囲でよいか |
| 低 | C-09 | 同じフォルダへの出力は上書き | 実験ごとに利用者が保存先を分ける運用でよいか |

### C-01〜C-03の影響を示す小さな例

バース1つに、V1が時刻0、V2が時刻2、V3が時刻5に到着するとする。
荷役時間は順に1、1、2時間とする。
正常時は各船が到着と同時に荷役を始められる。

V3を4時間早く申告すると、計画順はV1、V3、V2になる。
現実装ではV1が時刻1に終わった後もV3を待つため、時刻2に到着したV2は時刻7まで荷役できず、5時間待つ。
V3を待つ間にV2を荷役する運用なら、この例ではV2の待ち時間は0にできる。

この違いは、荷役時間の乱数の問題ではなく、固定計画を採用する運用前提の違いである。
早い申告の影響を説明する際は、固定計画によって空き時間が生じることも含めて説明する必要がある。

### C-04の補足

保存済みの `results/` の100試行は、係数をバースごとに固定した旧方式の結果であり、相関係数は約0.997だった。旧方式ではB1が常にB2より短かった。
2026年10月7日に船ごとの並べ替え方式を採用したため、現在は最速のバースが船によって変わる。共通の基準時間による相関は保つが、旧結果の相関係数や待ち時間を新方式の結果として扱わない。
新方式にも、3バースでは各船に速い・標準・遅い係数が1つずつ存在するという仮定がある。相関の強さや係数の幅の妥当性は引き続き確認する。

## 10. 受入条件と確認根拠

現状機能を要件として採用する場合の確認条件を示す。
「テスト対象」はテストコードに確認があるという意味で、本書の作成だけで追加検証を実行したという意味ではない。

| 要件 | 確認条件 | 主な実装 | 現在の確認根拠 |
| --- | --- | --- | --- |
| FR-01 | 同じseedのデータが一致し、バース別荷役時間に相関がある | `generate_ship_data()` | 再現性・相関の自動テスト対象。ただし研究上望ましい相関の値は未定 |
| FR-02 | 実到着と荷役時間を保持し、対象船の申告時刻だけ変更する | `apply_attack()` | 入力保持・対象以外の保持・0への丸めの自動テスト対象 |
| FR-03 | 申告時刻で順序が変わり、候補バースの優先順位どおり選ぶ | `assign_berths()` | 手計算、早い申告、バース選択の自動テスト対象 |
| FR-04 | 実到着前に開始せず、同じバースが重複しない | `assign_berths()` | 計画と実行の分離、物理的制約の自動テスト対象 |
| FR-05 | 各条件が同じ元データを使い、変更幅0で結果が一致する | `run_experiment()` | 元データ照合・変更幅0の自動テスト対象 |
| FR-06 | 手計算例で待ち時間・在港時間が一致する | `calculate_metrics()` | 一部指標の自動テスト対象。全8指標それぞれの独立した手計算テストはない |
| FR-07 | 同じ試行の差を集計し、1試行の標準偏差を空欄にする | `summarize_results()` | 変更幅0の差は自動テスト対象。CSVや集計の再計算一致は既存作業での確認記録あり |
| FR-08 | 試行0、船数1、バース0、不明な船、負や非有限の変更幅を拒否する | `run_experiment()`、出力側の `main()` | 不正設定の一部は自動テスト対象。CLIにも既存確認記録あり |

固定計画やデータ生成の仮定が、実港や卒論の研究目的に適することを証明するものではない。

## 11. 要件を確定するための判断欄

本書の優先確認点は、次の3つにまとめられる。

1. **研究対象**：申告情報の改ざんを研究し、実到着は変えないモデルを採用するか。
2. **運用方式**：事前に作ったバース・順番・開始時刻を守り、未到着船を待つ固定計画を採用するか。
3. **データと範囲**：仮定した到着・荷役データと特定船1隻の2攻撃で、まず予備比較を行う範囲でよいか。

この3点が合意できれば、現在のモデルを中心に要件を確定できる。
異なる意図があれば、対応するM・C項目とFR要件を先に修正し、その後に実装を合わせる。
初版作成時点ではコードや保存済みの実験結果は変更していなかった。今回の更新では係数配置の実装を変更し、保存済みの旧実験結果は維持している。
